# CoLabus — ядро совместной работы ИИ-агентов в вашем проекте

Проект-хозяин (host project) — это проект, над которым вы работаете.
Ядро CoLabus — инструмент, а не предмет работы.
Разработка самого ядра ведётся в репозитории разработки, не здесь.

Версия ядра: 2.0.3-pre.5 (точная сборка — в `PRODUCT-VERSION.json`). Этот репозиторий — продукт: его собирает скрипт
из репозитория разработки по списку разрешённого, руками он не правится, история у каждой сборки чистая.

Первый запуск: [одна страница с пятью командами](docs/product/QUICKSTART.md).

### Известные ограничения выпуска 2.0.3-pre.5

Это предварительный выпуск, и его ограничения названы здесь, а не спрятаны.

1. **Совет по моделям пока не даёт рекомендаций на настоящих запусках.** Он работает в режиме совета: печатает строки и никогда не меняет запуск, исполнителя выбирает человек. Приёмочные команды совета проходят на записанных запусках (результат N1 — 84 из 84, результат N2 — на 300 повторённых запусках), но на пяти настоящих запусках после посадки он не дал рекомендации ни разу (0 из 5) и показал верх списка моделей в 2 из 5; последний пересчёт на новейших пятидесяти настоящих запусках дал рекомендацию в 27 из 50, этого мало для финального выпуска. Для задачи высшего яруса сложности рамка запуска и движок считают разные ярусы, и верх списка остаётся пустым (причина `task-class-conflict`); состояния маршрутов устарели, поэтому ни один маршрут не называется пригодным к запуску (причина `route-state-stale`). Исправление — пакет ADVICE-LIVE-FIX: он в сертификации и в этот выпуск не входит. Планка владельца для финального 2.0.3: рекомендация запуска с маршрутом, который на деле сработал, не менее чем в 8 из 10 настоящих запусков после посадки пакета, читатели включены; владелец выбрал полосы уровня модели по классу задачи с видимым шагом вверх. Не полагайтесь на строки совета как на рекомендацию.
2. **Что осталось от pre.4 и проверено по линии.** Ярус модели `gpt-6.1-sol` не задан (читается как неизвестный) до решения владельца о рангах. Выпуск проверен на Windows (Git for Windows, Node 22 или новее); Linux и macOS не проверялись. Слой назначения советует и не запускает. Тихий узел фермы и RAM-раскладка вводятся по хостам: рабочий узел с полным RAM-режимом работает на девяти из десяти хостов шардов, остальные переходят по одному. Карантин нестабильных тестов: причины исправлены пакетами выпуска, строки закрывает оператор с доказательством прогонами фермы, срок строк записан в самих строках (`node .ai/bin/ops-tools/flake-quarantine.cjs list`) и продлевается только решением владельца. Метки журналов (шаг 1) и ворота усиления в этот выпуск вошли; шаг 2 меток не начат.
3. **Пределы, с которыми может столкнуться оператор хоста.** Корень проекта длиннее 188 символов ломает обновление и проверку (при 189 установка проходит, а обновление отказывает; от 227 — расчёт — отказывает и новая установка). Проверка реестра PowerShell на хосте читает только установленные файлы ядра, не файлы хоста; она не граница безопасности. Сканер секретов не раскодирует произвольные base64 и процентное кодирование. Тайм-аут запуска маршрута MiniMax не завершает внучатый процесс клиента. Потеря работы, найденная при чтении публикации (инструмент очистки деревьев после посадки убирал дерево, у которого работа лежала только в индексе, и архив её не сохранял), ИСПРАВЛЕНА в этом предварительном выпуске пакетом SWEEP-STAGED-FIX-2.0.3; не исправлено рядом: если у убираемых деревьев нет ни бандла, ни файлов для архива, папка архива не создаётся и строка журнала удалений после первого удаления не пишется. Посадочная проверка (GATE-CIRCLES, прошла через саму себя при посадке) работает в репозитории разработки с фермой; на установленном хосте без объявления фермы она отвечает «не применяется», а граница записи фермы процедурная. Гибель процесса внутри перехода короткого каталога-замка файла сигналов оставляет замок до явного восстановления (возраст не даёт права его убрать); одновременная работа старого и нового клиента файла сигналов не проверялась; ошибка записи после частичной записи не повторяется. Сканер секретов после маски и пробела отказывает слово из шести и более знаков как возможное значение (консервативно). Хост без компилятора .NET Framework печатает по одной строке `[reparse-query] fallback reason=no-compiler` на проверяемый путь. Часть поставляемых руководств называет пути, которых продукт не ставит; это унаследовано и ждёт решения владельца. Установленный хост, чей запуск отказывает `EFFORT REFUSED`, потому что реестр клиентов читается из образца ядра, ждёт следующего предварительного выпуска; правка образца ядра не является исправлением.

### Версия и дата сборки

В `PRODUCT-VERSION.json` поле `builtAt` — дата коммита-источника (`sourceSha`, время committer в UTC),
а не время запуска сборщика и не показание часов пользователя. Сборка детерминирована:
один исходный коммит и один манифест дают одну дату; несовпадение с местными часами не означает ошибку.

Это **предварительный выпуск 2.0.3-pre.5** поверх выпуска 2.0.2: действующие записи L0–L9 по актам владельца, строгие ссылки и LCC,
запуск ассистентов через ядро, подбор исполнителей по данным и единый реестр работ; к ним добавлены разбиение крупной задачи на части,
пакет задачи из записей ядра, роль хоста при установке, карантин нестабильных тестов и исправления состояния маршрутов
(это вошло в 2.0.3-pre.1), конвейер назначения по бенчмаркам в режиме совета, тихая ферма с RAM-диском и охраной томов,
планировщик фермы, места MiniMax и MiMo, отказ запуска из папки рантайма и состав выпуска из посадочных коммитов
(это вошло в 2.0.3-pre.2), а также список из трёх–пяти исполнителей при неизвестной линии сертификатора, чтение модели и лимитов места
из записей клиента в окне запуска, размер пакета задачи по качеству под одним пределом безопасности, квитанция запуска сертификации,
единый рабочий узел фермы с тихим запуском и RAM-диском, проверки инъекций и происхождения решений в валидаторе,
полный `AGENTS.md` из блоков источника и сокращённый `CLAUDE.md` (это вошло в 2.0.3-pre.3), а также исправления для пилота декомпозиции
проекта-хозяина: охрана операций обновляется вместе с ядром, одно имя семейства на производителя из таблицы ядра, отсутствующее усилие
читается как неизвестный ярус, заголовок реестра кандидатов мигрирует при обновлении ядра (это вошло в 2.0.3-pre.4), а также
данные совета по моделям с формулой силы и банком бенчмарков, полный RAM-режим рабочего узла фермы и предел тяжёлых прогонов,
очистка кэшей и временных папок после посадки, ворота усиления и проверка автора перед сертификацией, реестр использования PowerShell
с потолком, исправления нестабильных тестов у причины, исправленный маршрут MiniMax, метки журналов вне текста пользователя,
более быстрая установка, единый сканер секретов и рабочая документация со схемами потоков, а также посадочная проверка записей фермы
(GATE-CIRCLES: пакет садится, только когда программа сама видит зелёный полный прогон фермы точной головы и дерева, зелёные ворота продукта и отсутствие ждущего пина читателя),
обновление снимка цен каталога выбора (PRICE-REFRESH), исправления нестабильных тестов у причины в файле сигналов, пине каталога и диагностике ворот продукта (FLAKE-CAUSES-6),
исправление очистки деревьев после посадки, которая теряла работу, лежавшую только в индексе (SWEEP-STAGED-FIX), и исправления чтения публикации (PUB5-FIXES; это вошло в 2.0.3-pre.5).
Незавершённые улучшения будут в следующих предварительных выпусках и в 2.0.3. Наличие механизма подбора само по себе не означает акт его включения.

Исполнителя по-прежнему запускает человек, пока владелец не включит автоматическое назначение.

Посадка поезда и журнал запусков пишут файлы только через дескриптор, доказанный как файл на своём пути с настоящими папками; не закрыта лишь подмена папки другим процессом и её возврат между двумя соседними системными вызовами на каждой проверке пути, а для этого нужен контроль над планированием процесса.

## Что это

Несколько ИИ-ассистентов (Claude, Codex, Copilot, DeepSeek, GLM, Mistral, Qwen и другие) работают в одном
репозитории, не видя переписки друг друга. Единственный общий канал — файлы. Ядро задаёт, где что лежит и как
передаётся работа:

| Что | Где в проекте после установки |
| --- | --- |
| правила протокола для всех агентов | блок ядра в начале `AGENTS.md` |
| текущая задача и открытые вопросы | `.ai/TASK.md` |
| предлагаемый подход | `.ai/PLAN.md` |
| утверждённые решения (только дописываются) | `.ai/DECISIONS.md` |
| журнал каждой сессии | `.ai/worklog/` |
| рабочие слои ядра (процедуры, роли, схемы) | `.ai/core/` |
| инструменты: проверка, замок, передача, сессии | `.ai/bin/` |
| хуки Claude и Codex | `.claude/`, `.codex/` |

## Как установить в проект

Нужны Node.js 22 и git. Проект должен быть git-репозиторием без незакоммиченных изменений в отслеживаемых файлах.

```powershell
git clone <адрес этого репозитория> CoLabus
node CoLabus/docs/ops/kernel-install.cjs --target <путь к вашему проекту> --dry-run   # что будет сделано
node CoLabus/docs/ops/kernel-install.cjs --target <путь к вашему проекту>
```

Установщик ставит инструменты и слои ядра, создаёт недостающие файлы состояния `.ai/` (существующие не трогает),
дописывает свои строки в `.gitignore` и `.gitattributes` и вставляет блок ядра в начало `AGENTS.md` и `CLAUDE.md`
проекта. Ваш текст в этих файлах остаётся байт в байт после блока. Затем он запускает проверку и линт ядра в проекте
и печатает итог. Он ничего не коммитит и ничего не отправляет: посмотрите `git diff` и закоммитьте сами.

**Роль компьютера.** Компьютер сотрудника ставится одной командой с флагом `--host-role staff`; компьютер владельца —
`--host-role owner`:

```powershell
node CoLabus/docs/ops/kernel-install.cjs --target <путь к вашему проекту> --host-role staff
```

Установщик записывает `hostRole` в `protocol-manifest.json` проекта. На компьютере с ролью `staff` хуки сессии не пишут
журналы, замки и Evidence, а оператор получает опись доступа этого компьютера. Без флага уже записанная роль сохраняется
как есть, новая не придумывается. Неизвестное значение установщик отвергает до первой записи. Роль, которая уже
записана в проекте, флагом не меняется: вызов с другой ролью отвергается, пока в той же команде нет
`--confirm-host-role-change` (проект без записанной роли считается компьютером владельца). `--dry-run` печатает роль.
Флаги роли принимаются только с двумя дефисами и в нижнем регистре; форма `--host-role=staff` также допустима.
Манифест с BOM, неверным UTF-8 или повторяющимися ключами отвергается до записи; исправьте его явно перед установкой.
Те же правила действуют при вызове базового установщика с `--set-test-command`: подтверждённая смена роли и выбор
команды записываются вместе, а `--Verify` ничего не записывает.

**Окончания строк.** Протокол требует LF. Установщик сам записывает в `.gitattributes` блок
`BEGIN AI COLLABORATION PROTOCOL` с правилами `AGENTS.md text eol=lf` и `CLAUDE.md text eol=lf`, поэтому при включённом
`core.autocrlf=true` (по умолчанию в Git for Windows) вручную ничего добавлять не нужно. Проверка:
`git check-attr eol -- AGENTS.md CLAUDE.md` должна ответить `eol: lf` для обоих файлов. Закоммитьте `.gitattributes`
вместе с остальным результатом установки.

Набор пилота (слои L4–L6: обёртка запусков, сводка состояния, статистика запусков, мастер ключей) ставится вторым
шагом на отдельную ветку `kernel-pilot-*`:

```powershell
node CoLabus/docs/ops/pilot-install.cjs --target <путь к вашему проекту> --dry-run
node CoLabus/docs/ops/pilot-install.cjs --target <путь к вашему проекту> --keys=ask
```

Контракт этого установщика — `docs/ops/PILOT-INSTALL.md`; что делать после него — `docs/ops/PILOT-NEXT-STEPS.md`.

## Как работать

Каталоги `docs/ops/channels-catalog.json`, `docs/ops/mcp-catalog.json` и
`docs/ops/model-ladder.json` поставляются без проверенных записей проекта.
Перед настройкой подключений и рекомендаций заполните их собственными проверенными
данными. Пустой каталог не подтверждает наличие доступов или инструментов;
маршрут запуска модели задаётся явно. Схемы и проверки находятся в соответствующих
инструментах `docs/ops/`. Ядро и установщики не требуют заполненных каталогов.

Агенты читают `AGENTS.md` (Claude — через `CLAUDE.md`) и `.ai/TASK.md` в начале каждой сессии. Задачу ставит
владелец проекта. Как пользоваться слоями ядра и ежедневными командами — `docs/product/OPERATING.md`; руководство
оператора — `.ai/docs/PROTOCOL.md`; заметки по отдельным клиентам — `.ai/docs/`.

Проверка перед передачей работы, в корне вашего проекта:

```powershell
node .ai/bin/protocol-validate.cjs --root .
```

## Как обновить

```powershell
git -C CoLabus pull
node CoLabus/docs/ops/kernel-install.cjs --target <путь к вашему проекту> --update
```

`--update` заменяет управляемые файлы ядра новыми (старые копии — в `.ai/backups/`), обновляет блок ядра в
`AGENTS.md` и `CLAUDE.md`. Состояние проекта обновление не меняет, кроме одной записи: если реестр кандидатов
`.ai/runtime/CANDIDATES.md` несёт прежний заголовок каркаса pilot-install, заголовок заменяется на `# Operator candidates`
(остальные строки реестра остаются байт в байт). Отсутствующий реестр и реестр с верным заголовком не меняются; реестр, который не
проходит грамматику, останавливает обновление до первой записи, с причиной и исправлением. Журналы, `.ai/TASK.md`, `.ai/DECISIONS.md`,
`.ai/PLAN.md` и данные задач обновление не пишет (недостающие файлы состояния только создаются); `--dry-run` печатает план. Набор пилота обновляется командой
`node CoLabus/docs/ops/pilot-install.cjs --target <путь> --update` на ветке `kernel-pilot-*`.

## Что внутри этого репозитория

- `.ai/core/` — слои ядра; `.ai/bin/` — инструменты; `.ai/docs/` — документация для операторов;
- `docs/ops/kernel-install.cjs`, `docs/ops/pilot-install.cjs`, `docs/ops/pilot-kit.json` — установщики и набор пилота;
- `docs/ops/fleet/fleet.cjs` — инструмент для нескольких проектов на одной машине (`docs/product/OPERATING.md`);
- `templates/` — нейтральные шаблоны файлов состояния, обзора и промпта;
- `docs/product/RULES-IN-FORCE.md` — расшифровка идентификаторов решений, на которые ссылаются файлы ядра;
- `tests/` — тесты инструментов, которые запускаются в этом дереве: `node .ai/bin/protocol-test.cjs --root .`.
