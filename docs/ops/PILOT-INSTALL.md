# Установка набора ядра в проект

`docs/ops/pilot-install.cjs` обновляет уже установленный протокол и добавляет
набор из `docs/ops/pilot-kit.json` в отдельную ветку проекта. Запускайте команду
из репозитория ядра с ролью `source`; целевой Git-репозиторий должен иметь роль
`installed` в `protocol-manifest.json`. Для начального внедрения без установленного
протокола используйте предусмотренную проектом процедуру установки ядра.

## Команды

Сначала посмотрите план:

```text
node docs/ops/pilot-install.cjs --target <repo> --dry-run
```

Установка создаёт новую ветку с префиксом `kernel-pilot-`:

```text
node docs/ops/pilot-install.cjs --target <repo> --branch kernel-pilot-check --keys=no
```

Без `--branch` имя содержит текущую дату. `--no-commit` оставляет результат
для проверки без `git add` и коммита. Без этого флага успешная установка сама
создаёт коммит в новой ветке. `--dry-run` не создаёт ветку и не пишет файлы цели.

Обновление выполняется на уже выбранной ветке `kernel-pilot-*`:

```text
node docs/ops/pilot-install.cjs --target <repo> --update --dry-run
node docs/ops/pilot-install.cjs --target <repo> --update --keys=no
```

С `--update` несовместимы `--branch` и `--no-commit`. При наличии изменений
успешное обновление оформляется одним коммитом; при отсутствии — без коммита.

## Проверки до установки

Цель должна быть корнем Git-репозитория с чистым рабочим деревом и обычной
веткой, а не detached HEAD. Отслеживаемые, staged и untracked изменения мешают
установке; игнорируемые файлы в проверку чистоты не входят. Цель и репозиторий
ядра должны различаться. Новое имя ветки должно быть свободно и допустимо в Git.

Инструмент проверяет доступность обязательных файлов набора, UTF-8 файлов
`AGENTS.md` и `CLAUDE.md`, парность поддерживаемых маркеров блоков и конфликты
с файлами проекта. Файл слоя с другими байтами разрешено заменить, только если
он управляется протоколом либо указан в манифесте предыдущей установки.
Локальные правки ранее установленного слоя будут заменены после сохранения
снимка и перечислены в отчёте. Это следует оценить до запуска реальной установки.

## Что меняется

1. В системном временном каталоге создаётся снимок затрагиваемых файлов.
2. Для обычной установки создаётся новая ветка; обновление использует текущую.
3. `protocol-setup.cjs --Force` обновляет управляемые файлы и сохраняет свои
   резервные копии в `.ai/backups/` целевого проекта.
4. В `AGENTS.md` и `CLAUDE.md` возвращаются распознанные блоки маркеров проекта,
   которых нет в новом тексте. Пропавший текст вне блоков показывается в отчёте,
   но автоматически на прежнее место не вставляется. Проверьте эти различия.
5. Копируются корни набора и зависимости относительных `require()`, шаблоны
   и файлы слоёв по манифесту. Каркасы создаются только при отсутствии файла;
   существующие каркасы сохраняются. Прежние файлы, которых больше нет в наборе,
   остаются на месте и перечисляются.
6. В цели запускаются валидатор протокола и `protocol-core.cjs lint .ai/core`.
   Провал оставляет изменения без нового коммита.

Точный состав определяется манифестом, а не названием слоя. Скопированные
файлы, хэши, происхождение набора и ожидающие компоненты записываются в
`docs/ops/pilot-kit/KIT-MANIFEST.json`. Отчёт находится в
`docs/ops/pilot-install-report.md`; дальнейшие действия — в
`docs/ops/PILOT-NEXT-STEPS.md`.

## Ключи и внешние инструменты

`--keys=ask` — значение по умолчанию: при интерактивном терминале предлагается
мастер ключей, ответ по умолчанию отрицательный. Без терминала вопрос пропускается.
`--keys=no` только печатает команду мастера. `--keys=yes` запускает мастер без
вопроса и требует интерактивных stdin и stdout; иначе установка отклоняется
до изменений. Код завершения мастера не меняет результат установки.

Установщик не подключает MCP-серверы и не правит конфигурации клиентов.
Их настройка и отдельные сетевые проверки выполняются пользователем по
контрольному списку. Сам установщик не выполняет `push`, `fetch`, `pull`,
`clone` или настройку remote.

## Результат и восстановление

| Код | Значение |
|---|---|
| 0 | Установка или проверка плана завершена |
| 1 | Установка либо её проверки завершились ошибкой; новый коммит не создан |
| 2 | Неверные аргументы или отказ на предварительной проверке |

После ошибки изучите `git status`, отчёт и напечатанный путь снимка. Повторный
запуск откажется работать с грязным деревом. Не удаляйте изменения проекта ради
повтора; сначала сохраните их и выберите восстановление по фактическому состоянию.
Установщик печатает команды возврата к исходной ветке, но не удаляет ветки сам.

Ветка установки может содержать журналы проекта и записи запусков. Проверка
ядра не является проверкой пригодности этих данных для публичной публикации.
Установщик ничего не отправляет в удалённый репозиторий. В наборе есть образец
`docs/ops/pilot-kit/pre-push-guard.sample`; пользователь устанавливает его отдельно.
Он действует только в данном клоне, обходится `--no-verify` и не распознаёт
перенесённые cherry-pick копии коммитов.

Проверка `verify --layer` относится к заморозке исходного ядра и не является
обещанием работоспособности всех слоёв в установленном проекте. Проверяйте
валидатор, lint и собственные тесты целевого проекта.
