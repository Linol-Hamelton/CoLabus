# После пилотной установки ядра: что делает пользователь

Файл кладёт в проект установщик пилота (`pilot-install.cjs` репозитория ядра) и печатает его в конце установки. Установщик (и набор) НЕ входит в аккаунты, НЕ хранит ключи, НЕ ставит серверы, НЕ правит `.mcp.json` и клиентские конфигурации, НЕ правит `.gitignore` проекта и НЕ делает `git push`. Всё ниже выполняет пользователь в своём терминале. Основание: PROTO-DEC-0170.

Команды даны для корня проекта. Инструменты набора лежат под `docs/ops/pilot-kit/src/docs/ops/` (в репозитории ядра те же файлы лежат в `docs/ops/`).

## Публичный репозиторий: НЕ публиковать ветку установки

Ветка `kernel-pilot-*` держит установленное ядро, журналы сессий и записи запусков. Её нельзя отправлять в ПУБЛИЧНЫЙ репозиторий. Среди пилотных проектов Fight-for-the-moon публичный, SiteMVP приватный: перед любым push проверьте, куда он идёт (`git remote -v`, видимость репозитория в настройках хостинга).

Защита от случайного push (ставит пользователь; установщик в `.git` не пишет):

```bash
cp docs/ops/pilot-kit/pre-push-guard.sample .git/hooks/pre-push
chmod +x .git/hooks/pre-push
```

Хук отказывает (код 1), когда отправляется ссылка `refs/heads/kernel-pilot-*` (с любой стороны) или коммит, содержащий вершину локальной ветки `kernel-pilot-*` (например слияние ветки установки, отправляемое как `main`). Удаление ветки на удалённой стороне разрешено. Один осознанный push в приватный репозиторий: `ALLOW_KERNEL_PILOT_PUSH=1 git push ...`. Пределы: `git push --no-verify` обходит любой хук; коммит, скопированный через cherry-pick, хук не узнаёт; хук локален для клона (в репозиторий он не попадает), поэтому его надо поставить в каждом клоне. Проверка без push: `git branch --list "kernel-pilot-*"` и `git remote -v`.

## Чек-лист (по порядку)

1. **Запустите врача каналов.** Он только читает и пишет `.ai/runtime/CHANNELS-STATUS.md` (git-игнорируется):

   ```bash
   node docs/ops/pilot-kit/src/docs/ops/channels-doctor.cjs --root . --network
   ```

   Код 0: делать нечего. Код 1: в списке «Your actions» то, что может сделать только пользователь. `--network` нужен, чтобы клиенты проверили подключённые MCP-серверы; без него обязательные серверы показываются как `not-checked`.

2. **Войдите в браузере там, где врач это просит.** Строки `[login]` и `[authorize]`: например `claude auth login`, в Claude Code `/mcp`, затем выбрать сервер и авторизоваться; `codex mcp login <сервер>`. Врач эти входы не выполняет.

3. **Запустите мастер ключей или добавляйте ключи через `channels-keys` по одному.** Мастер по очереди спрашивает каждый ключ проекта (добавить или пропустить; по желанию потом входы клиентов claude, codex, vibe, mimo). Значение вводит пользователь в СВОЁМ терминале в скрытом приглашении; агенту ключ не передаётся, в чат, файл, журнал и аргументы команды не вставляется:

   ```bash
   node docs/ops/pilot-kit/src/docs/ops/channels-wizard.cjs
   node docs/ops/pilot-kit/src/docs/ops/channels-verify.cjs
   ```

   Перед каждым вопросом мастер показывает страницу выпуска ключа у провайдера и подсказку (что задать, например лимит кредита). Ответы: `a` добавить, `e` взять значение переменной, которая уже задана в окружении этой машины (без печати значения), `o` открыть страницу ключа в браузере, `s` пропустить, `r` заменить, `q` выйти. Вторая команда (`channels-verify`) только читает: один запрос на каждый имеющийся ключ, печатает имя, состояние и остаток, значений не показывает. На новой машине запустите мастер, затем проверку; машина, где переменные уже заданы, не перепривязывается.

   Или по одному (канал называет врач строкой `[add-key]`):

   ```bash
   node docs/ops/pilot-kit/src/docs/ops/channels-keys.cjs add <канал> --alias main
   node docs/ops/pilot-kit/src/docs/ops/channels-keys.cjs list
   ```

   Нужные каналы называет врач (строки `[add-key]`). Если ключ попал в чат: отозвать у провайдера и выпустить новый.

4. **Подключите три обязательных MCP-сервера: serena, codebase-memory, qmd** (PROTO-DEC-0170, обязательны в каждом проекте). Для каждого отсутствующего, неавторизованного или упавшего врач печатает действие `[connect]`, `[authorize]` или `[repair]` с закреплённой версией и ТОЧНЫМ фрагментом конфигурации клиента (Claude Code: `.mcp.json`; Codex: `~/.codex/config.toml`; Vibe: `~/.vibe/config.toml`); те же фрагменты в `docs/ops/pilot-kit/src/docs/ops/MCP-REQUIRED-AND-OPTIONAL.md`, раздел 1.3. Один раз установите пакеты (версии закреплены):

   ```bash
   npm install -g codebase-memory-mcp"@"0.11.0 @tobilu/qmd"@"2.8.3
   ```

   В фрагменте замените `<NPM_GLOBAL>` на вывод `npm root -g`. serena запускается через `uvx` на закреплённом коммите. Вставляет фрагмент пользователь. Проверка сервера: `node docs/ops/pilot-kit/src/docs/ops/mcp-schema-budget.cjs --config .mcp.json --server serena` (код 0: жив; то же для `codebase-memory` и `qmd`). Недоступный сервер не блокирует работу и не влияет на gate (раздел 1.6 документа).

5. **Запустите подборщик и выберите дополнительные серверы.** Он только читает проект и печатает короткий список; ничего не ставит:

   ```bash
   node docs/ops/pilot-kit/src/docs/ops/mcp-recommender.cjs .
   ```

   Выбор за пользователем. Описание для агента: `docs/ops/pilot-kit/src/docs/ops/skills/mcp-recommender/SKILL.md` (скилл лежит файлом и клиентам не подключается: попросите агента прочитать его). После выбора скилл записывает `docs/MCP-PROJECT.md`, установку выполняет пользователь.

6. **Добавьте строки `.gitignore`.** Установщик `.gitignore` проекта НЕ правит: допишите сами. Проверка после правки: `node docs/ops/pilot-kit/src/docs/ops/channels-guard.cjs gitignore-check --root .` (код 0: всё есть).

   ```gitignore
   .env
   .env.*
   !.env.example
   *.env
   *.key
   *.pem
   *.p12
   *.pfx
   *.jks
   *.keystore
   .credentials.json
   credentials.json
   auth.json
   secrets.json
   secrets.yaml
   secrets.yml
   secrets.toml
   .ai/runtime/
   ```

   Если подключили serena: она хранит данные проекта в собственном каталоге внутри дерева; добавьте этот каталог туда же. Предкоммитную проверку секретов (по желанию) печатает `node docs/ops/pilot-kit/src/docs/ops/channels-guard.cjs hook-snippet`; хук ставит пользователь.

7. **Повторяйте шаг 1, пока список «Your actions» не станет пустым** (код 0, `Nothing to do.`).

## Обновление набора позже

Когда в репозитории ядра (фабрике) вышла новая версия набора, его переустанавливают на той же ветке `kernel-pilot-*`, одним коммитом `chore(protocol): update the pilot kit to <sha>`. Дерево должно быть чистым; блоки-маркеры `CLAUDE.md`/`AGENTS.md`, файлы проекта и отредактированные заготовки сохраняются; повторный запуск ничего не меняет. Команды выполняются из фабрики (пример: продукт склонирован в папку `CoLabus`):

```powershell
node CoLabus\docs\ops\pilot-install.cjs --target <путь к проекту> --update --dry-run
node CoLabus\docs\ops\pilot-install.cjs --target <путь к проекту> --update
```

Для проекта из реестра парка то же делает `node CoLabus\docs\ops\fleet\fleet.cjs update-kit <проект>`. Ветку после обновления отправляют только в приватный репозиторий.

Что где: журнал установки `docs/ops/pilot-install-report.md`; слои L4, L5, L6: `docs/ops/PILOT-L4-L6.md`; каналы и ключи: `docs/ops/pilot-kit/src/docs/ops/CHANNELS.md`; откат установки печатается установщиком и записан в отчёте.
