# Каналы проекта (CLI, API, MCP) и ключи

Основание:  (слово владельца 2026-10-08). Класс B, инструменты в `docs/ops`, без изменений в `.ai/`. Правила протокола не меняются: вывод любых инструментов не Evidence и не gate; сертифицирующие сессии MCP и ключей не получают; удаление дублей и файлов остаётся под правилом удаления (инструмент только сообщает, решает пользователь).

Цель: новый проект получает готовую инфраструктуру каналов. Пользователь только входит в аккаунты и добавляет свои ключи; агент запускает одну справку, показывает ОДИН список действий пользователя и делает остальное.

Состав: каталог `docs/ops/channels-catalog.json`, справка `channels-doctor.cjs`, ключи `channels-keys.cjs`, мастер ключей `channels-wizard.cjs`, запуск с ключами `channels-env.cjs`, поиск дублей `channels-dedupe.cjs`, защита коммитов `channels-guard.cjs`, инвентарь имён ключей , общая библиотека `channels-lib.cjs`, скилл `docs/ops/skills/channels-onboarding/SKILL.md`.

## 1. Поток пользователя (по порядку)

1. **Справка.** Агент после установки ядра запускает одну команду и показывает список (скилл `channels-onboarding` делает это сам):

   ```bash
   node docs/ops/channels-doctor.cjs --network
   ```

   Результат: короткая сводка в терминале и файл `.ai/runtime/CHANNELS-STATUS.md` (не отслеживается git). В разделе «Your actions» все шаги пользователя, пронумерованы, по типам: `install`, `login`, `authorize`, `add-key`, `connect`, `repair`. Флаг `--network` разрешает команды, которые ходят в сеть (проверка входа `gh`, проверка здоровья серверов в `claude mcp list`); без него они пропускаются и помечаются `not-checked (network)`.
2. **Вход в браузерные каналы.** Для каждого пункта `login` пользователь сам выполняет указанную команду (например `claude auth login`) и входит под своим логином в браузере. Для MCP-серверов с пунктом `authorize` пользователь открывает клиент и авторизует сервер в браузере (Claude Code: команда `/mcp`; Codex: `codex mcp login <имя>`). Сервер получает доступ сам, ключ не нужен.
3. **Ключи.** Для каждого пункта `add-key` пользователь запускает команду из списка в СВОЁМ терминале и вводит значение в скрытое поле (оно не отображается):

   ```bash
   node docs/ops/channels-keys.cjs add openrouter --alias main
   ```

   Значение вводит только пользователь. Агент эту команду не запускает (раздел 5).

   **Все ключи проекта по очереди одной командой (мастер ключей):**

   ```bash
   node docs/ops/channels-wizard.cjs
   ```

   В установленном пилотном проекте: `node docs/ops/pilot-kit/src/docs/ops/channels-wizard.cjs`. Мастер один раз спрашивает псевдоним машины (по умолчанию из имени хоста; в проекте владельца `LAPTOP` или `DESKTOP`, PROTO-DEC-0176), затем идёт по сервисам каталога в фиксированном порядке. Для каждого он показывает сервис, имя или имена, которые читает проект, где они используются (`usedBy`) и лежит ли уже ключ для этого псевдонима. Ответы: `a` добавить, `s` пропустить (по умолчанию, пропущенный сервис остаётся нетронутым), `r` заменить (когда ключ есть), `q` выйти. Значение вводится только в скрытом приглашении: мастер его не знает, не показывает, не принимает в аргументах и не пишет в файл, хранение делает `channels-keys` (то же хранилище, та же проверка). Вторая фаза, необязательная: команды входа клиентов (claude, codex, vibe, mimo и остальные с командой входа в каталоге) печатаются точно как в каталоге и запускаются только после ответа `y`, с вашим терминалом; сбой входа мастер не останавливает. В конце сводка из одних имён (добавлено, пропущено, уже было, не предлагается, сбои) и по запросу врач только для чтения. Коды: 0 готово, 1 сбой хранилища, 2 неверный вызов или нет терминала и нет ответов в stdin (тогда ничего не меняется). `--only a,b` ограничивает список, `--list` печатает имена и состояние без вопросов. Установщик пилота предлагает эту команду в конце реальной установки (`--keys=ask|yes|no`, см. `docs/ops/PILOT-INSTALL.md`).

   Второй раунд (PROTO-DEC-0178, ). Перед каждым вопросом мастер показывает страницу выпуска ключа у провайдера (`keyUrl`), строку-подсказку по-русски (`keyHint`: где создать ключ, что задать, например лимит кредита у OpenRouter и бюджет ключа у Vercel AI Gateway) и дату проверки ссылки; ту же страницу и подсказку печатает `channels-keys add` перед скрытым приглашением и врач в строках `[add-key]`. Ответы мастера: `a` добавить, `e` взять значение переменной, которая УЖЕ задана в окружении этой машины, `o` открыть страницу ключа в браузере по умолчанию, `s` пропустить, `r` заменить, `q` выйти. `o` открывает только страницу из каталога и только по этому ответу, никогда сам; `e` предлагается, когда задана переменная с именем из каталога (каноническое имя или алиас) и для этого псевдонима ключа ещё нет; значение читается внутри процесса, проверяется и записывается через `channels-keys` как значение скрытого приглашения и нигде не печатается, в сводке только «taken from ИМЯ». Ноутбук владельца остаётся при своих привязках (переменные окружения пользователя): `e` нужен машине, где переменные уже есть, и переносу по просьбе, автоматически он ничего не делает. Имя `TELEGRAM_BOT_TOKEN` мастер НЕ берёт (старое резервное имя, на ноутбуке владельца оно отвечает как бот другого проекта `a bot of another project`, не ключ продукта): он предупреждает, а какой это бот, показывает `channels-verify`. В конце сводки мастер по запросу запускает `channels-verify` (по умолчанию нет), затем врача.

   **Проверка ключей (только чтение):**

   ```bash
   node docs/ops/channels-verify.cjs [--alias NAME] [--only a,b]
   ```

   Для каждого сервиса с ключом на этой машине (хранится для псевдонима или задана переменная каталога) один запрос GET к документированной конечной точке, указанной в каталоге (`key.verify`): OpenRouter `/api/v1/auth/key`, DeepSeek `/user/balance`, Cerebras и Groq `/models`, Hugging Face `/api/whoami-v2`, Vercel AI Gateway `/v1/credits`, GitHub `/user`, Cloudflare `/user/tokens/verify`, Telegram `getMe`. Печатает имя сервиса, откуда ключ (хранилище или переменная), состояние (`valid`, `rejected (401)`, `no answer`, `unknown`) и остаток, где его отдаёт конечная точка. Запрос с ключом уходит только на хост этого канала из списка допустимых хостов каталога (`key.verify.hosts`), только по https, переадресации не выполняются, таймаут 15 секунд; значения, заголовки и адреса с токеном не печатаются, ошибки сообщаются только кодом. Для сервисов без проверенной конечной точки (Dahl, Spacebunny, Better Design и другие) печатается «not checked: no verified read-only endpoint». Если имя бота из `getMe` не совпадает с ожидаемым (`key.expectedBot`, для `KEYSTORE_BOT_TOKEN` это `the bot of the project`), печатается строка WARNING. Код 0 всё проверенное валидно, 1 есть отклонённый ключ, нет ответа или неизвестное, 2 неверный вызов.

   **Проверка ссылок на страницы ключей (только для сопровождающего):** `node  [--only a,b] [--write]` делает один простой GET без ключа и без cookie к каждой `keyUrl` и пишет результат в поле `keyChecked` {date, how, status}: `ok`, `login-redirect` (страница отправляет на вход, ссылка живая), `moved`, `blocked` (401 или 403: перед страницей вход или проверка на бота, подтвердите в браузере), `unreachable` (не предлагается как рабочая). Ссылка без ответа в мастер не попадает.
4. **Повтор.** Пользователь (или агент по просьбе) снова запускает `channels-doctor.cjs --network`, пока раздел «Your actions» не станет пустым (код возврата 0). Ключи привязаны к устройству: на каждом компьютере шаги 2-4 выполняются заново.

Обязательные MCP-серверы (`serena`, `codebase-memory`, `qmd`; PROTO-DEC-0170) врач считает нужными всегда. Отсутствующий сервер он называет действием `[connect]`, неавторизованный `[authorize]`, упавший `[repair]` и печатает закреплённую версию и точный фрагмент конфигурации клиента (поле `connect` записи каталога; тот же текст, что в `MCP-REQUIRED-AND-OPTIONAL.md`, раздел 1.3, это закреплено тестом). Врач только печатает: `.mcp.json` и конфигурации клиентов он не правит. В проекте с пилотным набором инструменты лежат в `docs/ops/pilot-kit/src/docs/ops/`, и врач печатает команды с этим путём (`docs/ops/PILOT-NEXT-STEPS.md`).

Выбор каналов проекта: файл `docs/channels-project.json` (имена, без значений), его создаёт скилл после ответа пользователя:

```json
{ "schema": "channels-project/1", "want": ["claude", "codex", "openrouter", "telegram"], "declined": ["goose"], "updated": "2026-10-08" }
```

Всегда в списке нужных: `git`, `node` и обязательный минимум MCP (serena, codebase-memory, qmd). Остальное справка показывает как необязательное, пока канал не назван в `want` (или в `--want id,id`).

## 2. Имена ключей

Хранимое имя: `KEYSTORE_<SERVICE>_<ALIAS>`, например `KEYSTORE_OPENROUTER_MAIN`. `SERVICE` берётся из каталога (`key.service`: латиница и цифры, без подчёркивания); `ALIAS` придумывает пользователь (буквы и цифры, начинается с буквы, до 24 символов, хранится в верхнем регистре). Правило: **один ключ на пару (сервис, аккаунт)**. Второй ключ того же сервиса с другим alias команда `add` отклоняет, пока пользователь не передал явный `--second-account` (это другой аккаунт, а не копия).

Имя, которое читает программа (`key.env` в каталоге, единственное каноническое), отличается от хранимого: `channels-env` кладёт значение в окружение дочернего процесса под каноническим именем (например `OPENROUTER_API_KEY`). Другие имена того же сервиса (`key.aliases`) нужны для поиска дублей. Ключи, меняющие плательщика клиента (`billingSwitch`: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`), `channels-env` подставляет только при явном `--keys`; ключи Telegram: канонический `KEYSTORE_BOT_TOKEN`, старое имя `TELEGRAM_BOT_TOKEN` может принадлежать боту ДРУГОГО проекта, поэтому дубль сообщается, а решает владелец.

Каталог хранит для каждого ключа: `rotation` (как менять), `expiry` (срок: что известно, иначе «unknown»), `usedBy` (файлы, которые читают ключ: пустой список означает «ключ можно снять, если им никто не пользуется»), `scope: per-device`. Каналы и факты без подтверждения помечены `verified: false` и НЕ предлагаются (в первой версии: `xiaomi` без имени переменной, `dahl`, `typesafe`, `deepseek`, `webbee`); `google` исключён владельцем (OT-13).

Один ключ DeepSeek (PROTO-DEC-0178): канал `deepseek`, каноническое имя `DEEPSEEK_API_KEY`, хранимое `KEYSTORE_DEEPSEEK_<ALIAS>`. Прежние имена `DEEPSEEK_MAIN_KEY`, `DEEPSEEK_MENTOR_KEY`, `DEEPSEEK_MULTI_KEY` остались в каталоге только алиасами этого одного ключа (три имени были тремя ключами одного аккаунта: два с одинаковым остатком в USD, третий кошелёк в CNY; проект использует один ключ), и `channels-env` по-прежнему задаёт все эти имена дочернему процессу (флаг `inject` у алиаса) для кода, который их читает.

## 3. Команды

| команда | назначение |
|---|---|
| `node docs/ops/channels-doctor.cjs [--network] [--want id,id] [--no-mcp] [--json] [--root DIR]` | список действий пользователя; пишет `.ai/runtime/CHANNELS-STATUS.md`; код 0 — делать нечего, 1 — есть действия, 2 — ошибка запуска |
| `node docs/ops/channels-keys.cjs list [--json]` | имена сохранённых ключей на этом устройстве, канал, переменная, `usedBy`; значений нет |
| `node docs/ops/channels-wizard.cjs [--alias NAME] [--only a,b] [--list]` | мастер ключей: все сервисы по очереди, добавить или пропустить; затем по желанию входы клиентов; значение только в скрытом приглашении |
| `node docs/ops/channels-verify.cjs [--alias NAME] [--only a,b]` | проверка всех имеющихся ключей только для чтения: имя, состояние, остаток; значения не печатаются; запрос только на хост канала |
| `node  [--only a,b] [--write]` | проверка страниц выпуска ключей простым GET без ключа, запись `keyChecked` в каталог (для сопровождающего) |
| `node docs/ops/channels-keys.cjs add <channel> --alias <name> [--second-account]` | новый ключ; значение из скрытого запроса или из stdin |
| `node docs/ops/channels-keys.cjs rotate <channel> --alias <name>` | заменить значение; затем отозвать старый ключ у провайдера |
| `node docs/ops/channels-keys.cjs remove <channel> --alias <name> --confirm-alias <name>` | снять ключ с этого устройства; alias набирается дважды точно; в терминале без второго флага спросит повторно |
| `node docs/ops/channels-env.cjs run [--keys a,b] [--alias SERVICE=ALIAS] [--strict] [--dry-run] [--redact\|--no-redact] -- <команда>` | запустить команду, ключи только в окружении ДОЧЕРНЕГО процесса |
| `node docs/ops/channels-dedupe.cjs [--all] [--out FILE]` | отчёт о дублях (ничего не удаляет) |
| `node  [--write FILE] [--check FILE]` | инвентарь имён ключей по отслеживаемым файлам (только чтение), раздел 9 |
| `node docs/ops/channels-guard.cjs check --staged` / `gitignore-check` / `hook-snippet` | защита коммитов |

Команд «показать», «экспортировать», «скопировать значение» нет намеренно: `get`, `show`, `export`, `import`, `copy`, `sync` отклоняются.

`channels-env run`: если стандартный вывод не терминал (поток агента, конвейер), вывод дочернего процесса фильтруется и точные копии подставленных значений заменяются на `[REDACTED:ИМЯ]`. Фильтр ловит только точный текст: ребёнок, печатающий значение в base64 или по частям, его обходит, поэтому запускайте только доверенные команды. `--dry-run` печатает только имена переменных. На Windows команда из `.cmd`-оболочки (npm-шимы вроде `claude`) запускается через `cmd.exe`; аргументы со спецсимволами cmd (`& | < > ^ % " ! ( )`) отклоняются.

`channels-dedupe` ищет: один сервис под разными именами (с `file:line`), строки по форме секретов (те же шаблоны SECRETS, что в `launch-record-validate`), конфиги с литеральным ключом там, где нужна ссылка `${VAR}` (`.mcp.json`, `.vscode/mcp.json`, toml, yaml, env-файлы), и один ключ в нескольких местах (хранилище ОС, окружение процесса, пользовательское окружение Windows, env-файл, конфиг). Выводит только `file:line` и ИМЯ. Формальное совпадение шаблона (например присваивание `PATH_TOKEN = ...` в коде) тоже попадает в отчёт: решает человек.

Порядок отчёта фиксирован и не зависит ни от неотслеживаемых файлов, ни от порядка просмотра файлов: файлы сортируются, сервисы идут по алфавиту, внутри сервиса первым стоит каноническое имя из каталога, остальные по алфавиту.

**Локальный набор шаблонов (только `channels-dedupe` и `channels-guard`).** Поверх общего списка SECRETS из `launch-record-validate` эти два инструмента применяют `LOCAL_SECRETS` из `channels-lib.cjs`: голый токен Telegram-бота (`<цифры>:AA...`), `glpat-`, `hf_`, `npm_`, `sk_live_`/`rk_live_`, `SG.`, `dop_v1_`, `xoxe-`/`xoxb-`, `gsk_`, а также присваивания в нижнем регистре вида `api_key = "..."` и `token: "..."` с длинным значением (слово-заглушка в значении или ссылка `${VAR}` не считаются). Общий список SECRETS этим набором НЕ изменён (файл `launch-record-validate.cjs` не редактируется), остальные инструменты (`argvGuard`, самопроверка вывода, справка) используют только общий список. Расширять общий список или переносить в него локальные шаблоны может только владелец: это его решение. Набор не ловит произвольные строки с высокой энтропией; это известное ограничение.

## 4. Где лежат значения

- Windows: Credential Manager (generic credential, имя цели равно хранимому имени, `Persist = LocalMachine`, значение в UTF-16). Доступ через PowerShell и `advapi32` (CredRead, CredWrite, CredDelete, CredEnumerate), без сторонних пакетов; значение идёт в PowerShell через stdin в base64, в аргументы и в окружение процесса оно не попадает. Предел блоба Windows 2560 байт (около 1200 символов).
- macOS: Keychain через `security -i` (команда читается из stdin, значения в argv нет). Не проверено на реальной системе.
- Linux: libsecret через `secret-tool` (значение читается из stdin). Не проверено на реальной системе; список имён берётся из `secret-tool search` и из его вывода читаются только строки `attribute.name`.
- Репозиторий хранит только ИМЕНА (каталог). Значения не копируются между устройствами и не лежат ни в файлах проекта, ни в журналах, ни в промптах, ни в аргументах команд, ни в call-файлах.

## 5. Правила безопасности

1. Значение никогда не попадает в: репозиторий, журналы, `.ai/`, промпты, аргументы командной строки (argv виден в списке процессов), call-файлы, отчёты, вывод инструментов, транскрипт агента. Инструменты принимают значение только из скрытого запроса или stdin; любой аргумент в форме значения (`--value`, `--key=...`, строка по форме секрета) отклоняется.
2. Опасные способы ввода у клиентов, которых нельзя использовать: `cline auth -k <key>` и `claude mcp add -e KEY=<value>` кладут значение в argv или в конфиг. В `.mcp.json` ключ задаётся ссылкой `${VAR}`, клиент запускается через `channels-env`.
3. Один ключ на пару (сервис, аккаунт); дубли находит `channels-dedupe`, удаляет только пользователь.
4. Ротация: создать новый ключ у провайдера, `channels-keys rotate`, затем отозвать старый у провайдера. Сроки и места смены записаны в каталоге (`rotation`, `expiry`).
5. **Если ключ утёк** (попал в чат, журнал, коммит, лог, call-файл): (1) немедленно отозвать его у провайдера, не ждать; (2) выпустить новый и добавить `channels-keys rotate`; (3) найти место утечки по имени строки (`node docs/ops/channels-dedupe.cjs --all`), записать факт в журнал сессии БЕЗ значения; (4) если значение в коммите: коммит не переписывается без решения владельца, ключ считается скомпрометированным навсегда; (5) проверить, кто ещё использует ключ (`usedBy`).
6. Защита коммитов: `.gitignore` с перечнем имён хранилищ (`node docs/ops/channels-guard.cjs gitignore-check` показывает недостающие строки) и предкоммитная проверка `channels-guard check --staged`. Хук лежит в каталоге git, общем для всех рабочих деревьев, поэтому инструмент его не устанавливает: пользователь ставит его сам (`hook-snippet` печатает текст).
7. Правило по устройствам: ничего не копируется между машинами, на каждой запускается свой поток из раздела 1.
8. **Тестовое хранилище.** Переменная `CHANNELS_FAKE_STORE_FILE` (значения в обычном JSON-файле вместо хранилища ОС) принимается только вместе с `NODE_ENV=test` или с отдельной явной переменной `CHANNELS_ALLOW_FAKE_STORE=1`. Без них переменная игнорируется, используется настоящее хранилище ОС, а в поток ошибок идёт одна строка `[ignored CHANNELS_FAKE_STORE_FILE: ...]` с именем переменной (без её значения). При запуске команды через `channels-env run` обе переменные из окружения дочернего процесса удаляются. В рабочей среде эти переменные не задавать.

## 6. Что может и чего не может агент

Может: запускать `channels-doctor.cjs`, `channels-dedupe.cjs`, `channels-guard.cjs`, `channels-keys.cjs list`, `channels-env.cjs run --dry-run`; показывать список пользователю; записывать выбор каналов в `docs/channels-project.json`; запускать команду проекта через `channels-env run --keys ...`, если пользователь уже добавил нужные ключи; останавливаться и ждать.

Не может и не делает: получать, читать, печатать, просить в чате, подставлять в промпт или запоминать значение ключа; запускать `channels-wizard` и `channels-keys add`, `rotate`, `remove` (значение вводит пользователь в своём терминале, удаление решает пользователь); устанавливать клиентов и серверы, входить в аккаунты, менять клиентские конфиги и `.mcp.json`; удалять дубли и файлы. Сертифицирующие сессии не получают ни ключей, ни MCP.

## 7. MCP

Выбор необязательных MCP-серверов и скиллов делает подборщик : `docs/ops/mcp-recommender.cjs`, скилл `mcp-recommender`, документ `docs/ops/MCP-REQUIRED-AND-OPTIONAL.md` и каталог `docs/ops/mcp-catalog.json` (на момент написания в ветке `docs-mcp-required-claude`, не слита). Каталог каналов зеркалит из него только MCP-записи (скиллы не каналы). Порядок: подборщик предлагает и записывает выбор в `docs/MCP-PROJECT.md`; `channels-doctor` показывает, какие серверы клиенты видят и какие ждут авторизации; ключи серверов, которым они нужны, добавляются так же, как остальные.

Справка спрашивает у клиентов их собственные команды: `claude mcp list` (проверяет здоровье серверов, вызывает удалённые, поэтому только с `--network`), `codex mcp list --json`, `vibe config`. Из вывода сохраняются только имена серверов и слово-статус; командные строки, адреса и аргументы не сохраняются (в них бывают ключи). Формат вывода `vibe config` и реального `codex mcp list --json` при написании не проверялся на живых данных.

## 9. Инвентарь имён ключей и разрывы

Файл  перечисляет каждое имя ключа, которое встречается в отслеживаемых файлах проекта (`*_API_KEY`, `*_TOKEN`, `*_KEY`, `*_SECRET`, `*_PASSWORD`, `DATABASE_URL`): сервис, где оно читается (`путь:строка`), есть ли оно в каталоге, предлагает ли его мастер. Он создаётся командой `node  --write ` (только чтение файлов и `git ls-files`, без сети и хранилища; значений там нет). Имя, найденное в коде или документе и не предложенное мастером, обязано быть разрывом с причиной: безымянное имя делает `node  --check ` красным. Сервис добавляется в каталог только по улике с путём и строкой (поле `evidence`); имя переменной не выдумывается. Проверка ссылок `путь:строка` в документах и в улике каталога: `node  --catalog ` (только чтение, код 1 при битой ссылке). Инвентарь и проверка ссылок не входят в пилотный набор: это инструменты репозитория ядра. Второй раунд добавил в каталог сервисы без отдельного ключа ранее (Dahl и Typesafe помечены `unverifiedNote`: имя есть в коде, сервис не подтверждён; идентификатор `CLOUDFLARE_ACCOUNT_ID` назван как не секрет в `key.companions` и в хранилище не кладётся); `NPM_TOKEN` не добавлен, потому что отслеживаемый код его не читает.
